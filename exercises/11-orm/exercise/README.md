# Session 11 exercise: ORM mapping, generated SQL and N+1

## Files

- `models.py`: the six SQLAlchemy 2.0 models (`film`, `language`, `actor`, `film_actor`, `category`, `film_category`) with their relationships.
- `queries.py`: the three queries written with the ORM, run with `echo=True`, and checked against the handwritten SQL.
- `n_plus_one.py`: the N+1 on purpose, then the fix with `selectinload`.

## Task 2: generated SQL against handwritten SQL

### Q1: films per category

Handwritten:

```sql
SELECT c.name, count(*) AS films
FROM category c JOIN film_category fc ON fc.category_id = c.category_id
GROUP BY c.category_id, c.name
ORDER BY films DESC, c.name
```

Generated by the ORM:

```sql
SELECT category.name, count(*) AS films
FROM category JOIN film_category ON film_category.category_id = category.category_id
GROUP BY category.category_id, category.name
ORDER BY films DESC, category.name
```

Differences: the same query, with no table aliases. The ORM uses the full table names instead of `c` and `fc`, and the join condition is the same. Result: `Q1: 16 rows, same rows as handwritten SQL: True`.

### Q2: films longer than the average

Handwritten:

```sql
SELECT f.film_id, f.title, f.length
FROM film f
WHERE f.length > (SELECT avg(length) FROM film)
ORDER BY f.length DESC, f.film_id
```

Generated by the ORM:

```sql
SELECT film.film_id, film.title, film.length
FROM film
WHERE film.length > (SELECT avg(film.length) AS avg_1 FROM film)
ORDER BY film.length DESC, film.film_id
```

Differences: the scalar subquery is the same. The ORM names the aliased result `avg_1` and qualifies the column inside the subquery as `film.length`. Result: `Q2: 489 rows, same rows as handwritten SQL: True`.

### Q3: the 10 actors with most films

Handwritten:

```sql
SELECT a.actor_id, a.first_name, a.last_name, count(*) AS films
FROM actor a JOIN film_actor fa ON fa.actor_id = a.actor_id
GROUP BY a.actor_id
ORDER BY films DESC, a.actor_id
LIMIT 10
```

Generated by the ORM:

```sql
SELECT actor.actor_id, actor.first_name, actor.last_name, count(film_actor.film_id) AS films
FROM actor JOIN film_actor ON film_actor.actor_id = actor.actor_id
GROUP BY actor.actor_id
ORDER BY films DESC, actor.actor_id
LIMIT %(param_1)s::INTEGER
```

Differences: the ORM counts `film_actor.film_id` instead of `count(*)`. In a join, both are the same, because `film_id` is never null in `film_actor`. The `LIMIT` is a bound parameter (`%(param_1)s`, value 10) instead of a literal. Result: `Q3: 10 rows, same rows as handwritten SQL: True`.

**Summary:** the ORM generates the same logic as the handwritten SQL in all three cases. The differences are only aliases, the way the aggregate is written, and bound parameters. None changes the result.

```
Without eager loading: 101 SELECT statements (expected 101)
With selectinload:     2 SELECT statements (expected at most 2)
```

(The first three lines of each version are the same films and actors, so each version prints them once.)

| Version | SELECT statements | Expected |
|---|---|---|
| Without eager loading | 101 | 101 |
| With `selectinload(Film.actors)` | 2 | at most 2 |

**Why it happens:** the query for the films runs once. Then, for each film, accessing `film.actors` runs one more query, because the relationship is lazy by default. With 100 films, that is 1 + 100 queries.

**The fix:** `selectinload(Film.actors)` loads the actors of all 100 films in one more query, with `WHERE film_id IN (...)`. So the total is 2 queries, whatever the number of films.

The fixed version runs in a new session, so no object from the first version is reused.
